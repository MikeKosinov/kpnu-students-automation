2.1. Окремі гілки для завдань
Кожне завдання виконується у власній гілці від спільної гілки kn1-m25, а не прямо в ній. Так зміни одного студента не змішуються зі змінами інших, поки їх не переглянули. У pull request видно саме цей набір файлів, його можна повернути на доопрацювання, а спільна гілка лишається робочою.

2.2. Захист гілки від злиття без код-рев’ю
На спільну гілку ставлять правило: злити pull request можна лише після схвалення старшим розробником і після зелених перевірок. Рев’юер дивиться, чи зміна відповідає завданню і чи не ламає чужі тести. Без цього будь-хто міг би записати неперевірений код одразу в kn1-m25.

2.3. Навіщо CI/CD в управлінні проєктом
CI після кожного push сам збирає проєкт і запускає тести. CD готує вже перевірену збірку до викладення. Керівник бачить по статусу перевірки, чи зміну можна приймати, і не чекає, поки дефект знайде людина наприкінці.

Приклад. Сайт Automation Exercise, на якому побудовані тести цієї групи. Якщо в шапці зламається посилання Signup / Login, гість не зможе ні увійти, ні створити обліковий запис. Без CI такий дефект потрапляє в спільну гілку і виявляється вже під час ручної перевірки. З CI workflow Playwright Tests Desktop запускається на push гілки lz* і на pull request у kn1-m25. Збірка з проваленим тестом не зливається, тож зламаний вхід не стає кодом усієї групи.
